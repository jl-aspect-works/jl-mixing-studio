## Acceptance matrix additions / clarifications

The coordinated acceptance matrix should apply the following checks for this and subsequent RC candidates.

### D-00 — Create initial workspace

**Test:** Starting without an existing JL Mixing workspace, create a new workspace using Studio.

**Expected result:** The user can choose an appropriate location and create a valid JL Mixing workspace entirely from Studio, using Automation-owned workspace/studio creation semantics. The new workspace becomes available/configurable without requiring Terminal, Finder, or a Studio restart. Failed creation leaves the previous configuration unchanged and surfaces actionable feedback.

**RC1 result:** **Fail** — #238.

### D-01 — Configure/select workspace clarification

In addition to persistence and validation already required by D-01, the workspace `Change` interaction should use a native directory/folder picker rather than requiring manual entry of an absolute path. Candidate validation remains required before the path becomes authoritative.

**RC1 result:** **Fail** — #233.

### D-26 — Success feedback

Existing expected result remains: routine success feedback is transient and non-blocking, while warnings/errors remain actionable and persistent where required.

**RC1 result:** **Fail** — success toasts remain displayed instead of automatically clearing. See #234.

### D-28 — File-table modified-date consistency

**Test:** Compare Modified timestamps across Files, Client Files, Audio Prep, Revisions, Delivery, and any other project file tables that expose the same field.

**Expected result:** Shared file-table timestamps use one consistent Studio presentation format, including date/time punctuation, zero-padding, and am/pm treatment. Screens should consume a shared formatter where practical to prevent drift.

**RC1 result:** **Fail** — Files differs from the established Client Files/Audio Prep format. See #236.

## Enhancement observations

### Files screen navigation — #235

Re-evaluate whether the Files screen still benefits from its inner left-side project navigator now that the project-level navigation and shared file-browser behavior are established. This is a design/usability question, not a failure of the current frozen RC acceptance contract. Any layout change requires a focused product decision before implementation.

### Studio version visibility — #237

Consider exposing the authoritative packaged Studio application version in a low-noise diagnostics surface such as Settings > About. This is useful for RC/support verification but is not currently a release-blocking Daily Workflow requirement.

## RC1 disposition

The initial macOS pass has four tracked failures:

- #233 — Settings workspace path should use a folder picker;
- #234 — success notification toasts do not auto-dismiss;
- #236 — Files Modified date formatting is inconsistent;
- #238 — Studio cannot create a new workspace.

#238 is a direct Daily Workflow release blocker because initial workspace setup cannot be completed entirely from Studio. The remaining defects must be evaluated/fixed under the RC defect policy before the coordinated RC can be approved. #235 and #237 remain enhancement follow-ups unless explicitly promoted into the release gate.

After fixes, rerun D-00, D-01, D-26, D-28 and the affected packaged macOS checks against a new immutable RC tag rather than modifying `v2.0.0-rc.1`.
