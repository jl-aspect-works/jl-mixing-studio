## Acceptance matrix additions / clarifications

### D-00 — Create initial workspace

**Test:** Starting without an existing JL Mixing workspace, create a new workspace using Studio.

**Expected result:** The user chooses a parent location with a native folder picker, enters the required studio details, and completes the workflow with one **Create Workspace** action. Studio performs its non-destructive preflight internally, creates a new `Mixes` workspace there using Automation's existing `new-studio --root` semantics, validates it, makes it the configured workspace, and makes it available without Terminal, Finder, or a restart. Failed preflight returns to the form with actionable feedback. Once creation has begun, an uncertain result is not retried automatically.

**RC1 result:** **Fail** — #238.

**Fix status:** Implemented on the RC-fix branch. User verified on macOS that the simplified workspace Settings/create workflow is substantially improved and functioning as intended. Treat this as a **macOS branch/runtime Pass** for the revised interaction, but retain packaged acceptance as pending until exercised from the next immutable RC. Windows remains **Not run** until that RC is cut.

### D-01 — Configure/select workspace clarification

The workspace **Change Workspace…** interaction is a single user action: Studio opens the native directory/folder picker, validates the selected workspace automatically, and activates it only if validation succeeds. There is no separate user-visible Validate/Use step. Cancel or failed validation leaves the configured workspace unchanged.

**RC1 result:** **Fail** — #233.

**Fix status:** Implemented on the RC-fix branch. User verified the revised Settings workspace workflow on macOS and reported that it looks much better. Treat the revised interaction as a **macOS branch/runtime Pass**. Packaged macOS confirmation should still be included in the next RC pass, and Windows remains **Not run** until that candidate is available.

### D-12 / P-04 — Revision History formatting follow-up

**Test:** Inspect Revision History on supported platforms, including row height, title/badge alignment, description/date spacing, and behavior with multiple status badges.

**Expected result:** Revision rows remain visually aligned and readable without clipping, overlap, uneven vertical rhythm, or platform-dependent badge/date shifts. Formatting should remain stable under native platform font metrics.

**RC1 result:** Observation / visual follow-up identified during RC-fix review.

**Fix status:** Revision History sizing/alignment, line-height, and numeric-date rendering were hardened on PR #239. User visually verified the revised formatting on macOS and considers it **Pass** there. Windows visual verification is **Not run** and must be completed from the next packaged RC candidate before cross-platform acceptance is complete.

### D-26 — Success feedback

Routine success feedback is transient and non-blocking, while warnings/errors remain actionable and persistent where required. Success notifications must be removed after their display interval rather than merely becoming visually transparent.

**RC1 result:** **Fail** — #234.

**Fix status:** Implemented with explicit auto-dismiss behavior; packaged retest required.

### D-28 — File-table modified-date consistency

**Test:** Compare Modified timestamps across Files, Client Files, Audio Prep, Revisions, Delivery, and other project file tables that expose the same field.

**Expected result:** File-table timestamps use the established Studio presentation format without the inconsistent date/time comma and with consistent am/pm treatment.

**RC1 result:** **Fail** — #236.

**Fix status:** Implemented in the shared project file service with regression coverage; packaged retest required.

### Settings > About — #237

The application version is now in release scope for Studio 2.0. Settings contains a low-noise **About** panel displaying:

- authoritative packaged JL Mixing Studio version;
- detected JL Mixing Automation version when available;
- Automation API version used by this Studio release.

This is a diagnostics/support surface and does not add version information to daily project chrome.

**Fix status:** Implemented; packaged retest required.

## Deferred enhancement

The question of removing the Files screen inner left-side navigator is explicitly deferred to a later release. The 2.0 RC keeps the current Files layout unchanged. #235 remains the future design/usability tracker and does not block Studio 2.0.
