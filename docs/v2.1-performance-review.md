# Studio v2.1 performance review

## Scope

Reviewed the v2.1 daily-workflow paths called out in #275 with emphasis on unnecessary filesystem work, refresh amplification, list/filter computation, file enumeration, validation, and audio-preview initialization.

The highest-risk path is shared-workspace refresh because it can touch mounted/NAS/cloud-backed storage and is invoked during project navigation for freshness.

## Material findings

### 1. Background metadata refresh caused a recursive workspace storage scan

Before this pass, every successful `discover_default_workspace` call emitted one generic workspace-refreshed event. `useWorkspaceStorageSummary` subscribed to that event and invoked `summarize_workspace_storage`, which recursively walks the complete configured workspace and stats each file.

Project navigation intentionally performs a background workspace discovery when entering a project and when switching workflow screens. This meant a normal Overview → Client Files → Audio Prep sequence could couple each metadata refresh to a whole-workspace storage walk even though the storage total is not needed for project-screen correctness.

**Impact:** one background project refresh could cause one additional O(total workspace files/directories) recursive scan. On mounted or cloud-backed workspaces this is substantially more expensive than the metadata refresh itself.

**Fix:** workspace refresh events now distinguish metadata-only background refresh from explicit/full invalidation. Project/focus background discovery still refreshes authoritative workspace state, but does not invalidate the storage summary. Initial and explicit Refresh paths still refresh storage.

### 2. Overlapping workspace discovery requests performed duplicate work

The existing request-sequence guard prevented stale responses from replacing newer state, but it did not prevent multiple `discover_default_workspace` commands from running concurrently. A focus event, project navigation, and explicit refresh occurring close together could therefore perform redundant discovery work against the same shared workspace.

**Fix:** overlapping workspace discovery calls now share one in-flight request. A blocking/explicit caller joining a background request still upgrades the completed refresh to request storage invalidation.

**Deterministic effect:** multiple refresh requests issued while one discovery is pending result in one backend discovery operation instead of one operation per trigger.

### 3. Overlapping storage invalidations performed duplicate recursive scans

The storage hook used request IDs to ignore stale results but could still start a second recursive workspace scan while the first was running.

**Fix:** storage-summary refreshes now coalesce while a scan is in flight.

**Deterministic effect:** multiple invalidations while one storage scan is pending produce one `summarize_workspace_storage` command.

## Other reviewed areas

### Startup and route navigation

Startup performs workspace discovery, workspace-configuration read, and Automation-version check in parallel. The expensive storage summary runs asynchronously using the Tauri/Rust blocking pool rather than the UI thread. No architectural startup rewrite is warranted for v2.1.

### Project navigation and shared-workspace correctness

The authoritative workspace refresh on project entry/workflow-screen changes is intentionally retained. This is important for shared/mounted workspaces. The optimization removes unrelated storage indexing rather than weakening metadata freshness.

### Client Files validation

Client Files validation remains scoped to the active project and is intentionally refreshed when the Client Files workflow opens. No duplicate whole-workspace scan was found in that path during this review.

### Audio Prep and Project Files

Project Files uses a project/path-scoped listing rather than recursive workspace discovery for its displayed directory. Audio Prep similarly uses project-scoped data. These remain asynchronous and keep existing loading/last-known-data behavior. No broad filesystem cache was introduced late in the release because that would add invalidation complexity and weaken shared-storage correctness.

### Dashboard

Dashboard derives its cards and counts from the already-loaded workspace snapshot. The material Dashboard-adjacent cost was the recursive storage summary; that path is now decoupled from metadata-only navigation refreshes.

### Clients, Projects, Tasks, and Activities filtering

Filtering is local and linear over already-loaded snapshot arrays, with no backend/filesystem operation on each keystroke. The current expected dataset sizes do not justify virtualization or a new indexed-search architecture in v2.1. If real-world workspaces later show thousands of rows/events, virtualization/indexing should be evaluated as a separate change rather than added to the release candidate.

### Audio preview

Audio preview is loaded for the selected file and is not eagerly initialized for all listed audio files. Existing exclusive-playback and cleanup behavior is preserved. No material startup/navigation regression was found that warrants redesign before RC.

### Rust/Tauri blocking work

The recursive workspace storage summary is already executed through `spawn_blocking`, so filesystem traversal does not directly block the async/UI executor. The performance problem was call frequency/amplification, which this pass addresses at the caller/invalidation layer.

## Regression coverage

Focused tests now protect the performance behavior:

- overlapping workspace refresh requests are coalesced;
- metadata-only workspace refreshes do not rescan storage;
- explicit storage invalidation still rescans storage;
- overlapping storage invalidations are coalesced;
- the last successful workspace/storage result remains visible during refresh.

## Deferred optimizations

No large architectural rewrite is recommended for v2.1. Potential future work, only if representative production workspaces demonstrate a need:

- virtualized very-large table rendering;
- indexed/search-precomputed Tasks/Activities data;
- incremental workspace storage accounting rather than periodic recursive summary;
- filesystem watcher-based shared-workspace invalidation.

These would add substantial state/invalidation complexity and should be driven by measured production-scale need.
