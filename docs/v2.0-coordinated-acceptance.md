# JL Mixing Studio 2.0 / Automation 2.0 coordinated acceptance matrix

Status: **RC3 accepted; stable 2.0 release approved**

Target releases:

- JL Mixing Studio `v2.0.0`
- JL Mixing Automation `v2.0.0`
- Final accepted candidates: Studio `v2.0.0-rc.3` with Automation `v2.0.0-rc.1`
- Automation API contract: `1.0`
- Supported workspace metadata schema: `1.1.0`

Studio and Automation remain independently versioned products. The coordinated `2.0.0` numbering reflects this release plan only; Studio compatibility continues to be governed by Automation API version/capabilities and supported metadata schemas rather than product-version equality.

This document is the release-acceptance source of truth for the Daily Workflow release tracked by Studio issue #201.

## Release intent

Studio 2.0 turns the application into the normal project-management surface for a mix engineer working alongside a DAW. After one-time workspace configuration, normal project/revision/delivery work should not require Finder, Explorer, Terminal, or PowerShell.

Automation 2.0 supplies the authoritative workflow semantics and the additive API 1.0 capabilities required by Studio 2.0, including structured intake validation, Audio Prep provenance/status, revision-description editing, and managed Delivery status/package reconciliation.

The release question is:

> Can a mix engineer complete the approved Daily Workflow in packaged Studio 2.0 against packaged Automation 2.0, with authoritative state preserved across supported local/shared filesystems and with no release-blocking safety, compatibility, or packaging regressions?

## Scope freeze

In scope:

- Dashboard, Studio, Clients, Projects, Tasks, Activities, Settings global navigation;
- Project navigation: Overview, Client Files, Audio Prep, References, Revisions, Delivery, Files;
- local, NAS, and OS-mounted synchronized/cloud workspace paths;
- read-only Original Delivery browsing and validation visibility;
- Audio Prep browse, inline rename, safe delete, validation/provenance visibility;
- References add/manage/delete project-owned copies;
- Revisions create/manage/document/approve workflows;
- Delivery Notes, delivery readiness/status, package create/rebuild and supported package management;
- controlled project-wide Files tree and context-safe actions;
- shared workspace refresh/reconnect behavior;
- workspace and project storage summaries;
- macOS embedded audio preview through the shared WKWebView capability;
- Windows clean omission of embedded audio preview;
- installer/package behavior on supported Studio platforms;
- Automation API 1.0 compatibility and capability admission.

Explicitly out of scope:

- Windows embedded audio preview;
- Audio Prep Fix/Convert, repair, normalization, or format conversion;
- mutation of Original Delivery;
- generic Add/Import Files in Files or Audio Prep;
- provider-specific OneDrive/iDrive/NAS APIs;
- real-time simultaneous conflict merging;
- unrestricted filesystem browsing;
- waveform editing, playlists, A/B comparison, or DAW-like transport;
- external-reference linking instead of project-owned copies.

## Result values

Use one of:

- `Pass`
- `Fail`
- `Blocked`
- `Not applicable`
- `Deferred`
- `Not run`

Every `Fail` or unexpected `Blocked` result must reference a GitHub issue before the RC can be approved.

`Deferred` is appropriate when a test cannot be exercised in the current RC environment (for example, unavailable Apple Silicon hardware or a failure mode that cannot be safely/reliably induced during this acceptance pass). Deferred items do not imply a pass and must retain supporting automated coverage or prior evidence where applicable.

## RC defect policy

During RC acceptance:

- fix release blockers and genuine regressions only;
- do not expand the frozen 2.0 feature scope;
- do not opportunistically redesign/refactor unrelated code;
- repeat affected tests after each RC fix;
- publish a new RC tag rather than moving/reusing an existing RC tag.

A defect is release-blocking when it materially breaks an approved Daily Workflow, violates Automation API 1.0 compatibility, weakens filesystem/destructive-operation safety, corrupts or loses authoritative state, prevents supported installation/launch, breaks required macOS preview, or causes a required automated release gate to fail.
